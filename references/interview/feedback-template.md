# Feedback Template

Write for the candidate (mock) or the hiring committee (evaluation). Evidence first, adjectives last. Keep it under ~600 words unless asked for more.

```markdown
## Verdict
<Hire / Lean hire / Lean no hire / No hire> at <target level>.  Calibrated level: <e.g., solid Senior, not yet Staff>.
One-sentence reason: <the deciding evidence>.

## Scores (vs <target level> bar)
| Dimension | Score (1–4) | Key evidence |
|---|---|---|
| Problem navigation | | |
| Solution design | | |
| Technical excellence | | |
| Communication & collaboration | | |

## What went well
- <specific moment + why it is a level signal>
- …

## Biggest gaps (most important first)
1. **<gap>** — What happened: <quote/observation>. What a <target-level> answer sounds like: <1–3 sentences, concrete>.
2. …
3. …

## Crux check
- Crux of this question: <from case file>
- Did they find it unprompted? <yes/partly/no, when>
- Deep dives covered: <list, with depth reached: good / great / beyond>

## Practice plan
- Re-do <question> focusing on <deep dive>; target <time box>.
- Drill: <pattern/concept> → `/system-design learn <topic>` (or read `references/<file>` section <x>).
- Next mock: <question with similar crux> to test transfer.
```

## Writing rules
- Quote the candidate where possible; timestamps help.
- Claim only what the record shows: describe the candidate's actual proposal (not the nearest textbook label), and derive durations from timestamps rather than estimating.
- Each gap pairs with the better answer — feedback without a target is noise.
- Grade reasoning, not tool names. A well-argued DynamoDB is as good as the reference's Postgres.
- Don't pile on: list the 3 gaps that would change the outcome.
- If you gave hints, say which and how they affected the score.
